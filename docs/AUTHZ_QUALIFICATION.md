# Authorization-contract qualification — #626 (with the #627 retrieval baseline)

Generated by running [runtime_contracts/authz](../runtime_contracts/authz) against real implementations. The
verdict table is reproduced here for reading; the authoritative copy is
[docs/evidence/authz_qualification_matrix.json](evidence/authz_qualification_matrix.json), produced by
`python scripts/authz_matrix.py --check`, which fails if a verdict moves without the pinned expectation in
[tests/authz_contract/qualification.json](../tests/authz_contract/qualification.json) moving with it.

Scope note: **#626 is a contract, not a claim that anything enforces data boundaries.** This document exists
to say, per implementation and per invariant, what is enforced, what is not, and what has no seam at all.

## Verdicts

`UNSUPPORTED` means no seam exists that could satisfy the criterion. It maps to `INDETERMINATE` in the
verification vocabulary, never to PASS and never to N/A. A required sub-criterion that cannot be run demotes
its whole invariant to `UNSUPPORTED` even when every other sub-criterion passed.

| Invariant | agentic-os | agentic-os-enterprise |
|---|---|---|
| cross-tenant denial | **FAIL** | PASS |
| no privilege laundering | PASS | PASS |
| revocation during queued execution | PASS | PASS |
| stale authorization/cache epoch refusal | **UNSUPPORTED** | **UNSUPPORTED** |
| authorization before LIMIT | **FAIL** | **FAIL** |
| permitted edges survive, unauthorized excluded | PASS | PASS |
| adapter errors fail closed | **FAIL** | **FAIL** |

### The failures, with the code

**`cross_tenant_denied` — FAIL (kernel).** `PermissionsPlane.authorize`
([agentic_os/permissions.py:1251](../../tmp/kernel-e2/agentic_os/permissions.py)) takes no tenant argument and
never consults `Grant.tenant`; `GrantStore.add()`/`update()` cannot set the field. A grant tagged `acme`
authorizes `globex`. What the kernel *does* enforce is resource-tenancy at the execution seam:
`OwnerOnlyAuthority.authorize` ([agentic_os/execution_context.py:127](../../tmp/kernel-e2/agentic_os/execution_context.py))
denies a node acting on a resource owned by another tenant. The criterion is split accordingly
(`capability_boundary` / `resource_boundary` / `grant_tenant_tag`) so the passing half cannot carry the
failing half, and the kernel cell is FAIL on the tag sub-criterion alone.

**`authorization_before_limit` — FAIL (both, one cause).** `PolicyScopedRegistry.discover`
([agentic_os/mission/registry.py:183](../../tmp/kernel-e2/agentic_os/mission/registry.py)) is three lines:

```python
return [(c, s) for c, s in self._base.discover(need, k * 3) if self._permitted(c)][:k]
```

Over-fetch, filter, trim. With fifteen unauthorized capabilities ranked ahead of one permitted capability at
`limit=3`, the permitted edge is dropped silently — no error, no plan node, no receipt. The Enterprise
overlay reaches the same function through `MissionRuntime._scoped`
([agentic_os_enterprise/mission/runtime.py:93](../../tmp/ent/agentic_os_enterprise/mission/runtime.py)) and
inherits the defect unchanged. Nothing unauthorized is ever *offered*, so the confidentiality direction holds;
availability does not, and an agent that cannot see its own permitted capabilities cannot plan.

**`stale_epoch_refusal` — UNSUPPORTED (both).** The kernel ships the vocabulary — `decision_digest` and
`cache_entry_is_fresh` — and the predicate behaves correctly in isolation, but no kernel code caches an
authorization decision, so there is nothing stale to refuse. The overlay has no epoch field on `GrantRule` or
`AccessDecision` at all and re-evaluates rules per call. `bad_epoch_blind_cache` (a cache that writes an epoch
and never compares it) fails the criterion, which is the point: the day a cache is added, the suite catches
the mistake — but today the cell cannot be earned.

**`adapter_error_fails_closed` — FAIL (both).** Half the criterion holds on both planes: with the grant store
unreadable nothing is allowed, because the failure propagates out of the decision call. The other half does
not: no `authorization_decision` line is emitted and no ledger entry is written, so "who let this through" has
no answer and an operator sees a stack trace instead of a denial. Contrast the sealed-store path
([agentic_os/permissions.py:1254](../../tmp/kernel-e2/agentic_os/permissions.py)), which *does* deny with a
`policy_reason` — the pattern exists, it is just not applied to backend failures.

### What the passing cells do and do not mean

- **`no_privilege_laundering` PASS** on both planes: a role name with no grant of its own buys nothing; an
  explicit role grant is honoured only inside what it names; a cross-tenant delegation confers no capability
  permission. This is E-2's contribution and both `bad_role_bypass` mutants (pre-E-2 behaviour) fail it.
- **`permitted_edges_survive` PASS** covers graph edges. It does **not** cover document or row content — see
  #627 below.
- **`cross_tenant_denied` PASS (Enterprise)** rests on `IdentityPlane` refusing a request whose context tenant
  differs from the principal's, plus `DelegationAuthority` denying cross-tenant node access until a capability-
  scoped delegation exists. No scenario in that cell measures content crossing a boundary.
- One wiring fact the suite exposed and no test currently asserts: stage-2 compile authority comes from
  `Mission.policy_refs`, which the **caller** resolves; the identity plane feeds only stage-1 scoping and the
  dispatch gate. A caller passing a wide `policy_refs` is not identity-bound. Name it in the deployment
  contract.

Two honest caveats on that table:

- The `bad_epoch_blind_cache` controls fail the **weak** form of the check. The product cells are
  `UNSUPPORTED`, so there is no working code for the mutant to regress; the control proves the suite would
  catch the defect once a seam exists, not that it caught one today. The test records the distinction rather
  than counting it as the stronger result.
- `reference_tenant_bound_grants` still lands `UNSUPPORTED` overall even though it fixes the tenant tag: the
  kernel's `capability_boundary` sub-criterion has no request-tenant parameter for it to exercise. That is
  E-1's job, and it is why one sub-criterion being satisfiable does not upgrade a cell.

The two `reference_*` variants are used nowhere in the product. They exist so a FAIL is a statement about the
product rather than about the test: the criterion is achievable through the same seam the product uses.

## #627 retrieval baseline — recorded, not fixed

[tests/authz_contract/test_retrieval_baseline.py](../tests/authz_contract/test_retrieval_baseline.py) drives
redevops-rag's real ingest and retrieval paths. Seven criteria are **`xfail(strict=True)`** — they fail today,
the file knows it, and when somebody fixes the leak the XPASS turns the suite red rather than letting the
marking rot.

Measured, against the implementation (not asserted from the issue text):

- `Store._ensure_schema` columns are `id, document_id, filename, chunk_index, text, embedding, metadata,
  created_at`. No ACL, no tenant, no epoch column.
- No retrieval entry point takes an authority argument. `hybrid_search`/`semantic_search`/`bm25_search` accept
  `document_ids`, which is a caller-supplied subset, not authority — a caller may pass any subset, including
  the one containing another tenant's documents, and nothing checks it.
- An acme-only document, indexed alongside a globex document in the store the library documents today, is
  retrieved by a content query, ranks, is persisted in plaintext, and appears verbatim in the string
  `RAG.ask` hands a model.
- The store exposes **no** revoke/delete/forget interface. Withdrawal exists only as out-of-band SQL.
- Two criteria hold today and are pinned so regressions are noticed: the library logs no retrieved content, and
  `Store.semantic_search` failure inside `hybrid_search` is caught — which is itself the fail-open concern
  recorded as a seventh xfail: a dead vector feed silently becomes a BM25-only retrieval with no signal.
- **Not claimed:** that raw SQL deletion is or is not visible to another live indexer instance beyond what was
  measured (a second `Store` over the same DuckDB file did see the deletion; that is file-level visibility,
  not a revocation protocol, and no in-process cache was exercised because none exists).

The leak assertions are guarded by a non-vacuity test: the same marker is *not* retrievable when each tenant
has its own store, so the failures above are about authorization, not about a marker that could never appear.
Per-tenant physical separation is a mitigation a shell can apply today; it is not an ACL and it does not
survive a shared index.

Measured run of the lane itself, against redevops-rag `6e50d6d`:

```bash
REDEVOPS_RAG_ROOT=/path/to/redevops-rag/src python -m pytest tests/authz_contract/test_retrieval_baseline.py -q
# 21 collected → 14 passed, 7 xfailed (strict), 0 failed
```

Without the checkout the lane reports 21 **BLOCKED skips** and nothing else — a real DuckDB run and a skip are
different states and are kept that way. Before this record the lane could never leave the skip column: the

## Ordered remediation

Ordering is by what unblocks the most cells for the least churn, not by severity of wording.

1. **E-5 — filter before LIMIT** (`agentic_os/mission/registry.py:183`). Filter the permitted set, then trim,
   over the whole scoped pool; emit a machine-readable signal when permitted candidates are dropped.
   Unblocks two FAIL cells. `reference_filter_before_limit` shows the shape.
2. **E-6 — errors must be denials with receipts** (both planes). Convert store failures to a denied
   `AccessDecision` carrying `policy_reason` (`store_unavailable`), a ledger entry, an emitted envelope.
   Turns two FAIL cells green without touching any allow path, and it is the change that makes an outage
   debuggable instead of merely safe.
3. **E-1 — tenant-bound grants on the kernel plane.** Give `PermissionsPlane.authorize` a tenant context,
   refuse a grant whose tenant is set and differs from the request's, expose the tag through
   `GrantStore.add()/update()`. Until this lands, no kernel receipt may be described as tenant-bound and the
   `Grant.tenant` field is vocabulary.
4. **E-3 — one epoch, honoured.** Adopt a `(tenant, epoch)` pair on `GrantRule`/`IdentityPlane`, bump on
   `revoke_rule`, and key any decision cache by it through `cache_entry_is_fresh`. Until then `UNSUPPORTED`
   stands: it is not a pass, and a deployment that adds a cache tomorrow inherits a criterion it cannot
   satisfy.
5. **E-4/#627 — retrieval authorization.** Revocation interface on `Store`; authority inputs on the retrieval
   entry points; pre-index deny so unauthorized content never reaches readable storage; propagation of
   revocation to existing indexer instances. Until this lands, #626's `permitted_edges_survive` must not be
   cited as data-boundary enforcement — graph edges and document content are different boundaries, and only
   the first is tested green.
6. **Persist Enterprise revocation.** `revoke_rule` removes an in-memory rule; a restart or a second worker
   restores it. `revocation_during_queue` passes within a process and cannot be trusted across processes until
   revocation is durable and epoch-bearing (pairs with E-3).

## What a FAIL is measured against

Each cell above is run twice more in
[tests/authz_contract/test_negative_controls.py](../tests/authz_contract/test_negative_controls.py): once
against a `bad_*` variant that must fail the invariant it names, and once against a `reference_*` variant that
must pass it. A reference variant is a harness-only implementation of the criterion, driven through the same
seam as the product and used nowhere in it. It is not a product claim, it is not a row in the matrix, and its
only job is to show the assertion is satisfiable:

| Unmet cell | Witnessed by |
|---|---|
| `cross_tenant_denied` — agentic-os | `reference_tenant_bound_grants` |
| `stale_epoch_refusal` — both planes | `reference_epoch_honoring_cache` |
| `authorization_before_limit` — both planes | `reference_filter_before_limit` |
| `adapter_error_fails_closed` — both planes | `reference_error_denied_with_receipt` |

The pairing is keyed off the gaps pinned in `qualification.json` rather than off a live run, so it does not
drift with the environment, and a documented gap without a witness fails the suite: an unmet cell that nobody
could satisfy is a statement about the assertion, not about the product. `scripts/authz_matrix.py` prints the
pairing as `witness=…` and writes it into the JSON artifact as `satisfiability_witnesses`, with
`unmet_without_witness` listing any gap that has lost its proof.

## Whose receipt is this?

The suite declines to credit a decision it cannot place.
[runtime_contracts/authz/suite.py](../runtime_contracts/authz/suite.py) wraps every decision seam and rejects,
as **cross-talk**, a receipt whose envelope was emitted by a plane other than the implementation under test,
names a principal other than the one the scenario asked about, or decides a resource other than the one
requested. Three deliberately dishonest adapters in
[test_provenance.py](../tests/authz_contract/test_provenance.py) — one borrowing another edition's envelope,
one answering about the wrong subject, one replaying its first answer to every later question — must each fail
the cell, and an honestly attributed edition must never be flagged by the check. This matters most where both
planes are live in one process: a receipt from the wrong plane would otherwise read as enforcement the edition
under test never performed.

### Running it in the production profile

`AGENTIC_OS_PROFILE` is left unset in the commands above on purpose: `production` is a demand for *configuration*,
and an unprovisioned process fails in a way that reads, in a report, exactly like an authorization finding. Two
refusals do it — `agentic_os.mission.approval.default_replay_guard()` raises `ReplayProtectionNotDurable` without a
durable approval-replay store, and `agentic_os.mission.profile.assert_authority()` raises `ProfileError` for a
`MissionRuntime` whose authority guard is not durable. In that state five cells move off their pinned verdicts and
three known-bad controls lose their comparison baseline: eight failures that describe a deployment, not a plane.
Measured on the same checkouts as `qualification.json`, `AGENTIC_OS_PROFILE=production python -m pytest
tests/authz_contract -q` reports `8 failed, 74 passed` — five `test_cell_matches_its_pinned_verdict` cells (kernel
`revocation_during_queue`, `permitted_edges_survive`; overlay `no_privilege_laundering`, `revocation_during_queue`,
`permitted_edges_survive`), each with `ReplayProtectionNotDurable` or `ProfileError` in its detail, and three
`test_a_known_bad_variant_fails_its_invariant` controls that cannot compare a mutant against a plane that refuses
to start.

`agentic_os.mission.profile.check_environment()` is the product's own list of what production wants, printed by
`python -m agentic_os.mission.profile --require-production`:

| Requirement | What satisfies it |
|---|---|
| `AGENTIC_OS_PROFILE=production` | the variable itself (`AGENTIC_OS_REQUIRE_AUTHORITY=1` is an alias; anything else is an error, never a guess) |
| `AGENTIC_OS_REPLAY_DB` | a private, writable file. The product opens it as `SqliteReplayGuard` (WAL, `used_nonces`); there is no schema step, so pointing at the path *is* the setup |
| `AGENTIC_OS_AUTHORITY_DB` | a private, writable file opened as `AuthorityGuard(SqliteEnvelopeStore, SqliteLedger)` — the pair whose `durable` flag `assert_authority` reads. **The variable alone is not enough**: a `MissionRuntime` is refused unless a durable guard is handed to it, which a deployment's composition root does and a harness has to do at the same seam |
| `AGENTIC_OS_APPROVAL_SECRET`, 32+ characters | signs approvals and executions; unset makes both unavailable, never open |
| `AGENTIC_OS_CONTROL_TOKEN` or `AGENTIC_OS_TENANT_TOKENS` | without one an operator `/invoke` is disabled |
| `AGENTIC_OS_OPERATOR_ALLOW_ANONYMOUS` not set to `1` | refused in production, so it is deleted rather than left to the environment |

[test_durable_profile.py](../tests/authz_contract/test_durable_profile.py), over real stores built by
[durable_stores.py](../tests/authz_contract/durable_stores.py) — the product's own SQLite classes opening files in a

* **unprovisioned production** — the preflight names both stores, `default_replay_guard()` raises, and every cell

* **provisioned production** — the replay file holds the product's schema and really refuses a nonce it has

### Production authority: the two envelopes `permitted_edges_survive` needed

Provisioned but un-issued, the production run used to differ from the pinned matrix in exactly two places —
`permitted_edges_survive` for both editions — with `dispatched=[]`, a `failed` mission and an `AuthorityDeclined`
in the timeline. Cause: in production `MissionRuntime._authority_gate` refuses a node unless the mission has an
`AuthorityEnvelope` in a durable envelope store, and the contract scenarios minted none. That is production being
stricter than the contract, and neither folding the cells into the default-profile PASS nor leaving them as
unexplained FAILs was an honest report.

They can be provisioned through the product's own APIs, and now are:
[durable_stores.py](../tests/authz_contract/durable_stores.py) issues one envelope per mission at
`create_mission`, through `EnvelopeStore.put` — the call an owner's issuance path makes — with grants derived
**only** from two sources, and every grant names one capability. A mission's `policy_refs` are restated verbatim —
`Grant("billing.read")` matches a capability literally called `billing.read` and nothing else, so a permission name
buys no provider — and the capabilities that reach the envelope are the ones the **runtime's own registry**
declares, one by one, whose demanded permissions (`CapabilitySpec.permissions`, the operator's own declaration,
the same one the policy plane enforces) are all held by that mission. `billing.invoice` is issued because the
deployment registered it as demanding `billing.read`, which the mission declares.

There is no family expansion any more. An earlier revision of this fixture turned `billing.read` into `billing.*`
"because that is the kernel's family rule"; it is not the kernel's rule *at this seam* — an envelope grant is
fnmatch-matched against `node.capability` in `authority.evaluate` — and the expansion handed every mission
`billing.delete` and any other name in the family, registered or not. A family pattern now reaches an envelope
only where a `policy_ref` spells one out, which is a policy decision and has its own test. A mission that declares
nothing is issued an envelope that grants nothing, and its nodes are still refused. The mission must also name a
tenant, because the tenant is part of the authority key: a mission with none is given
`PRODUCTION_MISSION_TENANT` (`acme`), the same default the enterprise adapter already gives its missions. Neither
of these touches a criterion, an adapter, or a pinned
verdict — it is the composition root's job that a harness has to perform for itself, and it is asserted rather
than assumed in
[test_production_authority.py](../tests/authz_contract/test_production_authority.py):

* issuance is exact: a declared permission grants no capability by itself, the registry's two
  `billing.read` capabilities are each named separately, and nothing else is granted — a name no operator
  registered, a capability demanding an unheld permission, and `reports.monthly` are all refused
  `deny / out_of_scope` by the guard;
* a family wildcard behaves as the policy that wrote it: with `policy_refs = ["billing.*"]` the envelope reaches
  `billing.delete` — the name exact issuance cannot reach, which is exactly the width that must not be granted
  silently — and still stops at `reports.monthly`;
* the authorized plan dispatches exactly the edges it was granted and ends `succeeded`;
* `secret.exfiltrate` neither dispatches nor goes unrecorded, and `AuthorityGuard.check` answers it
  `deny / out_of_scope` **on the envelope the run issued** — so the PASS cannot be resting on the harness's own filtering;
* `guard.envelopes.revoke(mission_id)` stops the permitted edge again (`deny / revoked`), so the allow is live
  authority and not a cached yes; and revocation is durable — a second `SqliteEnvelopeStore` over the same file
  reports it;
* a mission with no issued envelope is refused with `no_authority`, which is the fail-closed control
  `test_durable_profile.py` already guards, left exactly where it was.


The no-checkout rows are quoted with `env -u` on purpose. An earlier revision of this table reported
"89 passed / 24 skipped" for a run that was in fact taken in a shell which still had `AGENTIC_OS_ROOT` and
`AGENTIC_OS_ENTERPRISE_ROOT` exported: it had checkouts, and the row described a posture that had not been
measured. Unsetting them exposed a real defect, now fixed — the two negative-control tests
(`test_every_invariant_can_be_broken`, `test_a_reference_variant_shows_the_criterion_is_satisfiable`) raised 11
failures on a machine with no checkout, because "no known-bad variant survived to be compared" and "this edition
is not on this machine" were the same empty list. They now distinguish the two: an absent checkout is a BLOCKED
skip naming the edition and its build error, while the anti-vacuity assertion itself is untouched and still fails
when the editions *are* here and a mutant has been deleted. With checkouts configured those same cells run: the
file is 18 passed / 3 skipped, the three skips being the pre-existing "qualification.json documents no gap here"
skips, not the missing-checkout ones.

Two things in that table were not true before this record, and both are now enforced rather than documented:

* **The checkout variables actually select the code.** `adapters._implementations.import_module` now calls
  `add_implementation_root` first. Before, `AGENTIC_OS_ROOT` / `AGENTIC_OS_ENTERPRISE_ROOT` /
  `REDEVOPS_RAG_ROOT` were documentation only — an installed copy answered, and the retrieval lane skipped with
  a message telling the reader to set a variable that would not have been read.
* **A recorded commit is bound to the imported code.** `test_a_recorded_commit_is_the_code_that_answered`
  resolves each plane from `module.__file__`, walks to its git working tree and compares `HEAD` with the SHA in
  `qualification.json` (plus that `base_commit` is an ancestor). A machine measuring a different checkout now
  fails the suite instead of reprinting SHAs it never ran.

The evidence artifact `docs/evidence/authz_qualification_matrix.json` is a snapshot, not a reproducible digest:
grant ids are random per run, so the recorded `detail` for `cross_tenant_denied/agentic-os` does not reproduce
byte-for-byte. `--check` gates on verdicts, which is the right thing to gate on; a reviewer comparing artifacts
should diff verdict triples, not bytes.

An implementation checkout that is not configured makes the relevant tests **skip with a BLOCKED reason**. No
cell is satisfied by the absence of a product, and no skip is reported as a pass.

## What is out of scope here

- **#45 staging qualification** runs on its own track (agentic-tests `api/test_permissions_postures.py`). Nothing
  in this suite substitutes stub results for staging evidence, and nothing here changes #45's security
  assertions. Its deterministic lane passes against a compliant posture and fails, case by case, against a
  violating one; the journeys against a deployed stack, and any desktop/mobile browser coverage, stay on that
  track and are not implied by anything in this matrix.
- **Deployments.** These verdicts are about library seams in a test process. They say nothing about a running
  stack, its configuration, or its network.
- **Production claims for either plane.** E-2 is reviewed independently; its acceptance is a human decision,
  and this document reports what its code does today rather than what it is intended to do.
